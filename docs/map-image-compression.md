# 地图压缩与等高线数据化评估

评估日期：2026-10-29。结论来自本机原件的离线编码与坐标校验，尚未替换线上资源，也未更改地图渲染器。本文的 MB 为十进制；MiB 为二进制。

## 建议

1. 底图按地图选择 WebP 或 AVIF，保留 WebP 回退；不将所有图片统一转成 AVIF。先由用户检查细节，再决定正式编码档位。
2. 需要持续放大、调整线色或按高度筛选的等高线，优先考虑保留矢量几何，使用整数差分二进制传输；第一阶段不减少精度、不删除点。
3. 普通 JSON 对当前 SVG 几乎没有体积收益；不要仅为了去掉 XML 而重写渲染器。
4. 若等高线只作为固定分辨率图片，透明无损 WebP 比本次无损 AVIF 更合适，但不能将栅格化称为无损保留矢量。
5. HTTP gzip/Brotli、资源格式和 Git 存储是不同维度。当前图床文件内容约 408 MB，其中地图约 360 MB；压缩网络响应不会缩小 Git 历史。限制解释见 [Git 与 CDN 限制](git-cdn-limits.md)。

## 样本与方法

现有地图目录中，61 个 SVG 合计约 220.13 MB，209 个 WebP 合计约 139.75 MB。数量与文件内容大小来自本次图床目录快照，不含 Git 历史，也不能直接当作网络流量。

使用本机归档并核验 SHA-256 的五个原件：达尔文丘、波兰、谢韦尔斯克-13 冬季底图，以及越南·高地、达尔文丘等高线。等高线精简处理与已发布文件的字节长度一致；体积表使用精简后的 SVG，不拿更大的原始导出文件作比较。

- PhotoCraft CLI 的 WebP 导出实测可用，但当前构建明确拒绝 AVIF 写入。因此统一使用已有 sharp 0.35.5／libvips 8.18.7／libaom 3.15.1 比较，无新增项目依赖。
- 底图维持原尺寸，以原件解码后的 8 位 sRGB 为参考。WebP 测试 Q85/90/95、effort 6；AVIF 测试 Q50/65/80、effort 4、4:4:4、8 位。不同编码器相同 Q 不代表相同质量。[sharp WebP](https://sharp.pixelplumbing.com/api-output/#webp)、[sharp AVIF](https://sharp.pixelplumbing.com/api-output/#avif)。
- SSIM 使用 FFmpeg 对解码后 RGB 单帧计算，PSNR 按 RGB 误差计算。两者不能替代玩家对细线、文字和纹理的人工检查。
- 等高线分别栅格化为 2048²、4096²，应用现行投影中的一次垂直翻转；比较透明度及可见 RGB。无损只指编码后与该分辨率栅格参考一致。
- gzip 和 Brotli 均固定质量等级 6，统计压缩产物字节；不是实际 CDN 的 Content-Encoding 或线路传输测试。
- 编码串行执行；单次耗时只作为本机成本参考。原生解码记录可能受 libvips 缓存影响，不将其作为浏览器、WebView 或手机解码基准。

原件、输出图、完整报告与实验脚本只保留在被忽略的 `artifacts/map-compression-20261029/`，不随 Git 或应用发布；本页只维护可公开的汇总结论。

## 底图：AVIF 收益取决于纹理

以下选择 SSIM 较接近的两个候选进行对照，并非认定视觉等质：

| 底图                     | 当前原件 | WebP 候选／SSIM         | AVIF 候选／SSIM         | AVIF 相对候选 WebP 的体积变化 |
| ------------------------ | -------- | ----------------------- | ----------------------- | ----------------------------- |
| 达尔文丘 4096²           | 9.81 MB  | Q95：5.922 MB／0.954543 | Q80：3.408 MB／0.953797 | 减少约 42%                    |
| 波兰 2048²               | 2.88 MB  | Q95：1.059 MB／0.947624 | Q80：0.592 MB／0.946400 | 减少约 44%                    |
| 谢韦尔斯克-13 冬季 2048² | 3.22 MB  | Q90：1.688 MB／0.984509 | Q80：1.545 MB／0.983891 | 减少约 8%                     |

对应编码耗时分别约为 WebP 11.7／2.3／3.2 秒，AVIF 38.7／12.4／19.4 秒。这里的三个原件为无损 WebP，上述候选均改变像素，不能将相对原件的全部减小归因于更好的无损压缩。

建议将 AVIF 作为底图候选格式，细节由用户检查；收益较低的图继续使用 WebP。实际采用前还需接入格式选择、可信 MIME、不同格式各自的哈希和 CORS 导出，不只改 URL 后缀。浏览器图片格式资料见 [MDN 图片类型](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types)。

## 等高线：去掉 XML 本身收益很小

越南·高地有 1,996 条路径、1,122,572 个点；达尔文丘有 170 条路径、42,645 个点。路径主要是 M/L 直线坐标，线宽和高度信息可复用。大部分字节来自坐标，XML 标签并非主要部分。

对两张图均保留 viewBox、裁切范围、共享样式、每条路径的线宽和高度标题，比较以下表示：

| 表示方式                     | 越南·高地原始字节 | gzip 6    | Brotli 6  | 达尔文丘 Brotli 6 |
| ---------------------------- | ----------------- | --------- | --------- | ----------------- |
| 现行精简 SVG                 | 19,748,407        | 7,320,970 | 6,202,492 | 260,688           |
| JSON 坐标数组                | 19,636,968        | 7,200,382 | 6,165,180 | 258,863           |
| 原精度整数差分二进制         | 4,449,784         | 3,791,441 | 3,610,661 | 155,010           |
| 坐标量化至 0.01 的差分二进制 | 2,260,991         | 1,580,478 | 1,383,649 | 83,198            |
| 简化线条后再量化的差分二进制 | 1,313,780         | 1,019,911 | 974,880   | 65,120            |

原精度方案将源坐标乘以 10,000，逐条路径对相邻坐标做整数差分，使用 ZigZag／varint 编码，并附带样式表、路径点数和样式索引。解码后逐点核对，两张图坐标误差均为 0。相对同等级 Brotli SVG，减少约 41.8% 和 40.5%；收益来自坐标编码方式，不能保证所有地图相同比例。

量化方案不删除点，但改变坐标：每轴最大误差约 0.005 个 viewBox 单位，在宽 4096 像素、viewBox 宽 1000 的画面上约 0.02048 像素，放大后同比增大。它不是无损方案。

简化方案使用 Ramer–Douglas–Peucker，容差对应 4096 像素画面上的 0.1 像素，再量化至 0.001；越南·高地剩 335,692 点、达尔文丘剩 21,151 点。未验证路径间拓扑关系，独立简化可能改变相邻线关系；不能仅凭体积与容差直接发布。

## 前端重绘的实际代价

几何数据可解码为 TypedArray，再建立 Canvas Path2D；也可重建受控 SVG。Path2D 支持保存路径和接收 SVG 路径字符串；OffscreenCanvas 可将部分绘制工作移到 Worker。[MDN Path2D](https://developer.mozilla.org/en-US/docs/Web/API/Path2D/Path2D)、[MDN OffscreenCanvas](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas)。

这些 API 并不自动解决百万点绘制成本。后续实施应先建立一次路径，再按相机变化重绘，避免每次拖动重新解码或构建全部路径。可考虑按高度／空间分组、视区剔除与缩放等级；量化、抽稀和分块的收益需分别验证。Canvas 在当前分辨率下仍会栅格化；放大时重新用矢量几何绘制才能保持精度。

相比当前将 SVG 用作图片，数据化增加了解码器、路径缓存、内存管理和导出适配的维护成本，不能仅根据传输体积宣称运行更快。越南·高地坐标本体若用两个 Float64 数组约占 17.96 MB，尚不包括索引、Path2D 和渲染表面；JSON 普通数组和对象的内存不能只按文件长度估计。

若使用 Worker，应沿用项目同源检查和失败回退。QMuse 的页面与静态资源可能跨域，不能重新引入跨源 Worker 构造失败阻断地图的问题。也不将一个很大的同步绘制任务直接塞进主线程。

正式协议可评估版本化 packed 整数字段或 protobuf；实验中的自定义格式仅用于体积验证，尚无生产安全边界、兼容和性能保证。当前“巨大等高线坐标 JSON 不进入前端／QMuse 包”的要求继续有效；新增资源格式、图床发布位置和公开范围需在实施任务中明确。

## 固定分辨率等高线：无损 WebP 优于本次无损 AVIF

| 样本      | 分辨率 | 无损 WebP | 无损 AVIF |
| --------- | ------ | --------- | --------- |
| 越南·高地 | 2048²  | 1.631 MB  | 3.765 MB  |
| 越南·高地 | 4096²  | 4.059 MB  | 10.225 MB |
| 达尔文丘  | 2048²  | 0.283 MB  | 0.836 MB  |
| 达尔文丘  | 4096²  | 0.647 MB  | 1.874 MB  |

以上编码还原的 alpha 和可见 RGB 最大误差均为 0，但栅格化已丢失无限放大能力。越南·高地 4096² 无损 AVIF 编码约 65 秒，WebP 约 4.1 秒；本次结果不支持用无损 AVIF 替代透明等高线。

单张 RGBA 栅格 2048² 约 16 MiB、4096² 约 64 MiB；这只是一个像素面的大小，浏览器还可能持有解码副本、纹理及导出画布。不能用下载文件小来推断运行内存低。

## 后续实施边界

- 保留原始 SVG 与来源哈希，不用压缩输出覆盖原件；不因为 GitHub／jsDelivr 大小误读而批量迁移。
- 第一阶段若采纳矢量数据化，优先原精度编码，再单独评估有损量化／抽稀；固定分辨率预览可与高精度矢量分层使用。
- 样式、透明度、裁切、路径顺序及投影必须一致；仍只对原等高线执行一次垂直翻转，复用同一屏幕与 PNG 导出几何。
- 确定采用格式后再更改 API 元数据、解码、缓存版本和发布工具；保留现行已验证资源回退及用户地图方案。
- 本次只完成离线评估与文档，不构成生产替换、全图压缩或前端重绘改造。
